# Avaya J129 v0.2.0 — Sprint 1

Estado: PLANIFICADO

## Objetivo

Iniciar v0.2.0 sobre la base estable de v0.1.0, priorizando dos líneas de trabajo del Endpoint Configurator:

1. resolver el descubrimiento/importación de endpoints J129 en VLANs/redes enrutadas donde la PBX no puede obtener la MAC por ARP/Nmap;
2. comenzar la capa de capacidades configurables por modelo para que el J129 deje de depender de parámetros fijos y pueda exponer opciones reales desde Endpoint Configurator.

La v0.1.0 permanece congelada y no se modifica.

## Prioridad 1 — Discovery inter-VLAN

### Evidencia

Producción: `cei-pbx02.lamundial.hn`

PBX:

```text
10.3.40.2
```

Caso remoto observado:

```text
IP: 10.3.32.21
MAC: C8:1F:EA:C3:D6:B2
ruta: 10.3.32.21 via 10.3.40.1 dev eth0 src 10.3.40.2
```

Nmap desde la PBX detecta que el host remoto está activo, pero no entrega `MAC Address:` al cruzar routing. El `detect_endpoints` estándar de Issabel solo procesa hosts cuando dispone de MAC para compararla contra `mac_prefix`.

### Historia de usuario

Como administrador de una central Issabel con teléfonos distribuidos en VLANs de voz enrutadas, quiero que Endpoint Configurator pueda incorporar endpoints usando una pareja confiable `IP + MAC`, manteniendo el mismo flujo estándar de fabricante/modelo, Accounts, Apply y provisioning.

### Primera implementación

Entrada mínima:

```text
IP
MAC
```

Ejemplo conceptual:

```bash
j129-import-endpoint --ip 10.3.32.21 --mac C8:1F:EA:C3:D6:B2
```

El nombre final y la forma de integración se decidirán durante implementación.

Fuentes futuras de IP+MAC:

- entrada explícita/manual;
- tabla ARP del gateway/router de la VLAN de voz;
- leases DHCP;
- MikroTik RouterOS/API;
- inventario de red confiable.

La integración automática con MikroTik no es obligatoria para el primer incremento, pero la interfaz debe diseñarse para permitirla después.

## Prioridad 2 — Capabilities por modelo

Sprint 1 debe crear la base para que las opciones del Endpoint Configurator dependan de las capacidades reales del modelo y no de hardcodes dispersos.

Matriz inicial J129 a investigar/documentar:

```text
SIP                         soportado
1 cuenta SIP                v0.1.0 confirmado
idioma / locale             investigar + preparar selección
interfaz Web                habilitar/deshabilitar desde configuración
softkeys / menú local       investigar y mapear parámetros
conferencia tripartita      investigar y validar con Asterisk
presencia / BLF             investigar SUBSCRIBE/NOTIFY y compatibilidad Asterisk
TLS / certificados          investigar provisioning, trust store y SIP TLS
background / branding       investigar imágenes y restricciones del modelo
Auto Answer / 3PCC          investigar en LAB; relacionado con Test 48
codec / DTMF / QoS          inventariar parámetros soportados
NTP / timezone              mantener y normalizar configuración
```

No todas estas funciones tienen que quedar implementadas en Sprint 1. Sí deben quedar clasificadas como `SUPPORTED`, `UNSUPPORTED`, `REQUIRES-LAB`, `REQUIRES-FIRMWARE`, o `UNKNOWN`, con evidencia y ubicación de configuración cuando se conozca.

## Entregables funcionales Sprint 1

1. mecanismo LAB para importar/descubrir un endpoint remoto mediante `IP + MAC` sin romper el discovery local stock;
2. pruebas de idempotencia y colisiones IP/MAC;
3. definición de una estructura de capabilities por modelo reutilizable para futuros Avaya y otros fabricantes;
4. primer conjunto de opciones visibles/configurables del J129, priorizando:
   - idioma/locale;
   - habilitar/deshabilitar Web UI;
   - parámetros básicos de softkeys/menú si la documentación/firmware lo permite;
5. documentación de conferencia, presencia/BLF, TLS/certificados, background/branding y 3PCC aunque su implementación completa se difiera a sprints posteriores;
6. scripts reutilizables que surjan durante el trabajo deben quedar bajo `scripts/` y no enterrados dentro de workflows.

## Requisitos de arquitectura

1. No modificar `Avaya.py` para resolver discovery inter-VLAN.
2. No modificar Accounts ni el manejo estándar de credenciales SIP.
3. No reconsultar secretos SIP desde DB.
4. No imprimir ni almacenar secretos SIP, Web Admin, tokens, contraseñas, cookies, hashes o claves privadas.
5. Validar formato de IP y MAC antes de cualquier escritura.
6. Normalizar MAC al formato esperado por Endpoint Configurator.
7. Resolver fabricante usando `mac_prefix` existente en `endpointconfig`.
8. Reutilizar, cuando sea técnicamente razonable, la misma semántica de inserción/actualización de `detect_endpoints`.
9. Evitar duplicados por MAC.
10. Tratar colisiones IP/MAC de forma explícita y documentada.
11. Mantener una sola cuenta SIP para J129 hasta una release que cambie formalmente ese límite.
12. Primera implementación y toda capacidad nueva se valida primero en LAB/Audit.
13. No modificar producción hasta completar pruebas y release independiente.
14. Las opciones específicas de modelo deben declararse en una capa de capabilities/plantilla, no duplicarse innecesariamente en core.
15. No introducir una UI paralela de credenciales SIP.

## Flujo objetivo

```text
Red local
  -> detect_endpoints / Nmap estándar

Red enrutada
  -> fuente confiable IP+MAC
  -> helper/importador
  -> fabricante por mac_prefix
  -> inventario Endpoint Configurator

Inventario
  -> modelo
  -> capabilities del modelo
  -> Accounts estándar
  -> opciones de provisioning permitidas
  -> Apply estándar
  -> Avaya.py
  -> provisioning
  -> SIP
```

## Criterios de aceptación

- J129 remoto alcanzable por IP pero sin MAC visible desde Nmap puede agregarse con IP+MAC reales.
- El endpoint se asocia a Avaya por OUI y al modelo J129 sin duplicados.
- Reimportar misma IP+MAC es idempotente.
- Cambiar IP manteniendo la misma MAC actualiza sin duplicar.
- Colisión IP con MAC diferente se maneja explícitamente.
- Discovery local stock sigue funcionando sin regresión.
- Accounts estándar conserva una sola cuenta SIP.
- Apply/provisioning siguen funcionando como v0.1.0.
- Existe una matriz de capacidades J129 versionada.
- Al menos idioma/locale y Web UI quedan definidos como opciones de configuración o documentados como bloqueo técnico con evidencia.
- No se exponen secretos en logs.
- Suite LAB específica PASS antes de crear release v0.2.0.
