# Avaya J129 v0.2.0 — Sprint 1

Estado: PLANIFICADO

## Objetivo

Agregar soporte de descubrimiento de endpoints Avaya J129 ubicados en redes/VLAN enrutadas distintas a la interfaz local de la PBX, sin modificar el flujo estándar de Accounts, Apply, provisioning ni la clase vendor Avaya validada en v0.1.0.

## Evidencia que origina este Sprint

Producción: `cei-pbx02.lamundial.hn`

PBX:

```text
10.3.40.2
```

J129 remoto:

```text
IP: 10.3.32.21
MAC: C8:1F:EA:C3:D6:B2
```

Ruta observada:

```text
10.3.32.21 via 10.3.40.1 dev eth0 src 10.3.40.2
```

El host remoto responde ICMP, pero la PBX no mantiene una entrada ARP/neighbor directa para `10.3.32.21` porque está detrás de routing.

Comparación de Nmap:

Red remota:

```text
nmap -T4 -sP -n 10.3.32.21
Host is up
SIN línea MAC Address
```

Red local:

```text
nmap -T4 -sP -n 10.3.40.20
Host is up
MAC Address: C8:1F:EA:C3:D5:97 (Avaya)
```

El `detect_endpoints` estándar de Issabel usa Nmap y sólo procesa endpoints cuando recibe una MAC que puede comparar contra `mac_prefix`. Por eso un host remoto puede ser alcanzable por IP y aun así no entrar automáticamente al inventario del Endpoint Configurator.

## Historia de usuario

Como administrador de una central Issabel con teléfonos distribuidos en VLANs de voz enrutadas, quiero que Endpoint Configurator pueda incorporar un endpoint a partir de una pareja confiable `IP + MAC`, para mantener el mismo flujo estándar de fabricante/modelo, Accounts, Apply y provisioning aunque la PBX no pueda obtener la MAC mediante ARP local.

## Alcance Sprint 1

Diseñar y validar en LAB un mecanismo complementario de discovery/importación para redes enrutadas.

Entrada mínima esperada:

```text
IP
MAC
```

Ejemplo conceptual:

```bash
j129-import-endpoint --ip 10.3.32.21 --mac C8:1F:EA:C3:D6:B2
```

El nombre y CLI definitivo se decidirán durante implementación.

## Requisitos

1. No modificar `Avaya.py` para resolver discovery.
2. No modificar Accounts ni el manejo estándar de credenciales SIP.
3. No reconsultar secretos SIP desde DB.
4. No imprimir ni almacenar secretos SIP, Web Admin, tokens o contraseñas.
5. Validar formato de IP y MAC antes de cualquier escritura.
6. Normalizar MAC al formato esperado por Endpoint Configurator.
7. Resolver fabricante usando `mac_prefix` existente en `endpointconfig`.
8. Reutilizar, cuando sea técnicamente razonable, la misma semántica de inserción/actualización de `detect_endpoints`.
9. Evitar duplicados por MAC.
10. Tratar colisiones IP/MAC de forma consistente con Issabel.
11. Mantener soporte de una sola cuenta SIP para J129 mientras no exista una release separada que cambie ese límite.
12. La primera implementación debe probarse únicamente en LAB/Audit.
13. No modificar producción hasta completar pruebas y release independiente.

## Fuentes futuras de IP + MAC

Sprint 1 debe soportar inicialmente entrada explícita/manual para aislar la lógica.

Posteriormente se evaluará automatización desde una fuente que conozca ambas capas, por ejemplo:

- tabla ARP del gateway/router de la VLAN de voz;
- leases DHCP;
- MikroTik RouterOS/API;
- inventario de red confiable.

La integración con MikroTik no forma parte obligatoria del primer incremento funcional del Sprint 1.

## Flujo objetivo

```text
Red local
  -> detect_endpoints / Nmap estándar

Red enrutada
  -> fuente confiable IP+MAC
  -> helper de importación
  -> fabricante por mac_prefix
  -> inventario Endpoint Configurator
  -> Accounts estándar
  -> Apply estándar
  -> Avaya.py
  -> provisioning
  -> SIP
```

## Criterios de aceptación

- Un J129 remoto alcanzable por IP pero sin MAC visible desde Nmap puede ser agregado usando su IP+MAC reales.
- El endpoint queda asociado a `Avaya` por OUI.
- El modelo J129 puede quedar seleccionado/asociado sin crear fabricantes o modelos duplicados.
- Reimportar la misma IP+MAC es idempotente.
- Cambiar IP manteniendo la misma MAC actualiza el endpoint sin duplicarlo.
- Una colisión IP con MAC diferente se maneja de forma explícita y documentada.
- Accounts estándar sigue permitiendo una sola cuenta SIP.
- Apply genera provisioning igual que en v0.1.0.
- No se exponen secretos en logs.
- Suite LAB específica PASS antes de crear release v0.2.0.

## Fuera de alcance

- firmware 4.x;
- idioma español XML;
- multicuenta;
- cambio automático de contraseña Web Admin;
- modificación del core de Accounts;
- reemplazo del discovery local estándar;
- despliegue automático a producción.
